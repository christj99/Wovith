# Wovith Provenance Graph
### Tracking the lineage of every cell result

---

## 0. About this document

This document specifies how Wovith tracks the provenance of cell results — the answer to "where did this come from?" — which is the technical foundation for the right-click → why → lineage feature the concept doc commits to as Wovith's trust moat.

Provenance, in Wovith, has three audiences:

1. **The user, asking why** — "why is this email in my Decisions Today cell?" The lineage panel shows: source (Gmail), the filter that matched (`from is in vip-contacts and state is unread`), the agent enrichment if any (Sonnet 4.6, prompt fingerprint X), the freshness window (fetched 2 minutes ago).

2. **Wovith itself, debugging** — when a cell returns something unexpected, the provenance graph is the audit trail. When two devices show different results for the same cell, the provenance graphs are compared.

3. **External auditors and compliance** — for Trust tier users (per the GTM doc), provenance is exportable as a verifiable record of what data flowed where.

The model adopted: **W3C PROV-DM** (PROV Data Model), the W3C-vetted standard for representing provenance. PROV-DM has three core classes — Entity, Activity, Agent — and a small set of relations. It's domain-agnostic but specializes cleanly. Wovith's specialization is straightforward.

---

## 1. The W3C PROV-DM model in 60 seconds

PROV-DM has three primary classes:

- **Entity**: a thing whose provenance is being tracked. In Wovith: a cell value, an MCP response, an agent response, a user input.
- **Activity**: something that happens over time and acts on entities. In Wovith: cell evaluation, MCP call, agent call, user action.
- **Agent**: a party responsible for an activity. In Wovith: the user, a specific Wovith subsystem, an LLM provider.

And the relations between them:

- `used`: Activity used Entity (cell evaluation *used* an MCP response)
- `wasGeneratedBy`: Entity was generated by Activity (an MCP response *was generated by* an MCP call)
- `wasAssociatedWith`: Activity was associated with Agent (an MCP call *was associated with* the user as the requesting party)
- `wasDerivedFrom`: Entity was derived from Entity (a transformed RecordSet *was derived from* a raw RecordSet)
- `wasInformedBy`: Activity was informed by Activity (cell B's evaluation *was informed by* cell A's evaluation, because B depends on A)
- `actedOnBehalfOf`: Agent acted on behalf of Agent (a Wovith subsystem *acted on behalf of* the user)

These six relations cover essentially every provenance question Wovith needs to answer.

## 2. Wovith's specialization of PROV-DM

### 2.1 Entity sub-types

```typescript
type ProvEntity = 
  | CellValueEntity
  | McpResponseEntity
  | AgentResponseEntity
  | UserInputEntity
  | CacheEntryEntity

type CellValueEntity = {
  kind: 'cell-value'
  id: string                  // unique entity ID
  cellId: string
  lensId: string
  hash: string                // content hash of the value
  size: number                // bytes
  createdAt: number
  metadata: {
    rendererId: string
    itemCount?: number        // if the value is a record set
    summary?: string          // human-readable summary
  }
}

type McpResponseEntity = {
  kind: 'mcp-response'
  id: string
  connectorId: string
  toolName: string
  paramsHash: string          // hash of params (not the params themselves, for privacy)
  responseHash: string
  size: number
  createdAt: number
  ttlMs: number               // when this response will be stale
}

type AgentResponseEntity = {
  kind: 'agent-response'
  id: string
  provider: 'anthropic' | 'openai' | string
  model: string
  promptFingerprint: string   // hash, not the prompt
  responseHash: string
  size: number
  inputTokens: number
  outputTokens: number
  createdAt: number
}

type UserInputEntity = {
  kind: 'user-input'
  id: string
  source: 'voice' | 'text' | 'tap'
  contentHash: string         // hash of the user's input string
  createdAt: number
}

type CacheEntryEntity = {
  kind: 'cache-entry'
  id: string
  cacheLayer: 'mcp' | 'agent' | 'cell-value'
  key: string
  storedAt: number
  retrievedAt: number
}
```

The crucial design choice: entities store **hashes**, not the actual content. The hash is enough to compare entities for equivalence ("is this the same value?") and to look up the actual content from the data layer (where it's appropriately cached or persisted). It avoids inflating the provenance graph with payload duplication.

### 2.2 Activity sub-types

```typescript
type ProvActivity =

  endedAt: number

type McpCallActivity = {
  kind: 'mcp-call'
  id: string

  endedAt: number
  status: 'completed' | 'failed' | 'timeout'
  durationMs: number
  cacheHit: boolean
}

type AgentCallActivity = {
  kind: 'agent-call'
  id: string
  provider: string
  model: string
  startedAt: number
  endedAt: number
  status: 'completed' | 'failed'
  inputTokens: number
  outputTokens: number
  cacheHit: boolean
  budgetUnits: number
}

type TransformActivity = {
  kind: 'transform'
  id: string
  description: string         // 'filter where age > 5 days', 'sort by date desc', 'take 10'
  appliedAt: number
}

type UserActionActivity = {
  kind: 'user-action'
  id: string
  action: 'authored-cell' | 'edited-cell' | 'dismissed-item' | 'confirmed-action' | string
  performedAt: number
}

type CacheReadActivity = {
  kind: 'cache-read'
```

## 3. The provenance record per cell

Every cell value carries a provenance record:

```typescript
type ProvenanceRecord = {
  // The cell value entity itself
  resultEntity: CellValueEntity
  
  // The activity that produced it
  evaluationActivity: CellEvaluationActivity
  
  // The graph of upstream activities and entities
  upstream: ProvenanceNode[]
  
  // Relations
  relations: ProvenanceRelation[]
}

type ProvenanceNode = {
  entity?: ProvEntity
  activity?: ProvActivity
}

type ProvenanceRelation = {
  type: 'used' | 'wasGeneratedBy' | 'wasAssociatedWith' | 
        'wasDerivedFrom' | 'wasInformedBy' | 'actedOnBehalfOf'
  subject: string            // entity or activity ID
  object: string             // entity or activity ID
}
```

A typical Decisions Today cell's provenance graph might look like:

```
cell-value-X (Decisions Today result)
  ← wasGeneratedBy ←  cell-evaluation-1
                       used → cache-read-1
                                → wasGeneratedBy → cache-entry-A
                                                    → wasDerivedFrom → mcp-response-1
                                                                        → wasGeneratedBy → mcp-call-1
                                                                                            → wasAssociatedWith → system:mcp-client
                       used → transform-1 (filter where state=unread)
                       used → transform-2 (filter where from in vip-contacts)
                       used → transform-3 (sort by date desc)
                       wasAssociatedWith → user:chris
                       wasAssociatedWith → system:runtime
```

Reading this back to the user as "why":
- The cell evaluated at 14:30
- It read from Gmail (via MCP call to gmail.threads at 14:28)
- The result was cached (TTL 60 seconds)
- Filters applied: unread, from VIP contacts
- Sort: by date descending
- No agent enrichment in this cell
- The user (you) is the agent of record

## 4. Storage

### 4.1 Where provenance lives

Provenance records are stored alongside the audit log in SQLite (see `wovith_data_architecture.md`, section 4 on the local cache layer). They're append-only — once recorded, an activity or entity is never modified.

```sql
CREATE TABLE prov_entities (
  entity_id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  details_json TEXT NOT NULL,   -- the typed fields
  created_at INTEGER NOT NULL,
  -- The cell that this entity is "for" (the top of its provenance chain)
  cell_id TEXT,
  lens_id TEXT
);

CREATE INDEX idx_prov_entities_cell ON prov_entities(cell_id);
CREATE INDEX idx_prov_entities_kind ON prov_entities(kind);
CREATE INDEX idx_prov_entities_created ON prov_entities(created_at DESC);

CREATE TABLE prov_activities (
  activity_id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  details_json TEXT NOT NULL,
  started_at INTEGER NOT NULL,
  ended_at INTEGER NOT NULL,
  cell_id TEXT,
  lens_id TEXT
);

CREATE INDEX idx_prov_activities_cell ON prov_activities(cell_id);
CREATE INDEX idx_prov_activities_started ON prov_activities(started_at DESC);

CREATE TABLE prov_agents (
  agent_id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  details_json TEXT NOT NULL
);

CREATE TABLE prov_relations (
  relation_id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  subject_id TEXT NOT NULL,
  object_id TEXT NOT NULL,
  recorded_at INTEGER NOT NULL
);

CREATE INDEX idx_prov_relations_subject ON prov_relations(subject_id);
CREATE INDEX idx_prov_relations_object ON prov_relations(object_id);
```

Two indexes per table by the common access patterns: by cell (for "show me lineage for this cell") and by time (for "what happened recently").

### 4.2 Retention

Provenance can grow large. Retention policy:

- **Active cells**: provenance kept for the lifetime of the cell's current value
- **Historical cells**: when a cell's value is recomputed, the old provenance is moved to an archive table (`prov_archive_*`) and retained for 30 days
- **Background data**: anything older than 30 days is purged unless the user has explicitly pinned that cell value

Pinning a cell value is a future Trust-tier feature ("I want a permanent record that on Date X, my agent did Y"). At v1, the 30-day window is enforced.

### 4.3 Per-device

Provenance is device-local, like the audit log. Each device records its own activities. Cross-device provenance reconciliation is a v3+ concern.

## 5. The recording API

The cell runtime's eval context (from the cell runtime doc, section 4.3) exposes provenance recording:

```typescript
// In the eval context:
context.recordRead(source: 'gmail.threads', payload: McpResponse) 
context.recordTransform(description: 'filter where state=unread', input: Entity, output: Entity)
context.recordCall(target: 'agent', model: 'sonnet', input: Prompt, output: Response)
context.recordUserInput(input: string)
```

The runtime wraps every operation in these recording calls. The recording is automatic — cell evaluation code doesn't need to think about provenance; the framework records it.

Internally, recording produces:
- A new entity for the input (if not already recorded)
- A new activity for the operation
- A new entity for the output
- Relations connecting them (used, wasGeneratedBy, wasDerivedFrom)

All recording is synchronous to the cell evaluation but writes happen asynchronously (batched and flushed) to keep the eval path fast.

## 6. The "why" UX

When the user right-clicks a cell or a specific item in a cell and asks "why is this here?":

### 6.1 Per-cell lineage view

```
Why this cell shows what it shows:

Source: Gmail (read-only)
Filters applied:
  • Unread messages
  • From VIP contacts (Chris's curated list)
Sort: By date, newest first
Last fresh: 2 minutes ago
Cached at: 14:28
Agent enrichment: None

What data Wovith saw:
  73 threads matched. 12 shown.
```

The view is structured prose, derived from the provenance graph. The user sees the human-readable summary, not the raw graph.

### 6.2 Per-item lineage view

For a specific item in the cell ("why is this thread here?"):

```
Why this thread appears:

Matched: state=unread, from=Hye (in VIP list)
Source: Gmail
Fetched: 2 minutes ago
Thread ID: 1842736...
```

This is faster to read because it's just about one item — no need to summarize the whole pipeline.

### 6.3 Full graph view (power user)

For users who want the raw graph (debugging, audit, curiosity), a "Show the full graph" affordance reveals the actual PROV-DM nodes and relations as an interactive graph visualization. This is a power feature, hidden behind one tap from the lineage view.

## 7. Granularity: per-result vs per-cell

A cell with 12 items shown to the user. Do we record 12 provenance entries (one per item) or 1 (for the whole cell)?

**Default: per-cell.** The provenance is for the cell evaluation. Individual items are referenced as fragments of the result.

**Drill-down: per-item on demand.** When the user asks "why this specific item?", the provenance system queries the cell's evaluation activity, applies the same filters/transforms to a fresh fetch of the source, and walks the chain for that specific item. This is computed lazily, not pre-recorded.

This keeps provenance storage bounded. A cell with 1,000 items doesn't produce 1,000 provenance entries.

Exception: cells with agent enrichment record per-item provenance for the enrichment step, because each enrichment is its own LLM call with its own cost and lineage. The cell's overall provenance plus 12 enrichment-level entries (for 12 items) is the right level.

## 8. Provenance and CRDTs

The data architecture doc keeps provenance out of Automerge (it's device-local SQLite). This is the right choice because:

- Provenance is append-only — no merge benefit
- Each device records its own — there's no canonical version
- Provenance can be large; syncing it would burn bandwidth
- A cell that evaluates on Device A has provenance on Device A; the same cell evaluating later on Device B has its own provenance there

The downside: cross-device "why" answers aren't unified. If the user asks "why" on Device B for a cell they originally observed on Device A, they get Device B's provenance, not Device A's.

This is an acceptable simplification at v1. The user's intuition matches it: "why does this *device* show this *now*?" is more meaningful than "why has it ever shown this?"

## 9. Export for compliance

For Trust-tier users, provenance can be exported as a verifiable record:

```typescript
type ProvenanceExport = {
  exportedAt: number
  exportedBy: string          // user ID
  deviceId: string
  windowStart: number
  windowEnd: number
  
  entities: ProvEntity[]
  activities: ProvActivity[]
  agents: ProvAgent[]
  relations: ProvenanceRelation[]
  
  // Signed manifest
  manifest: {
    sha256: string             // hash of the export
    signatureAlgorithm: 'ed25519'
    signature: string          // signed with device key
  }
}
```

The export is signed with the device's private key (held in secure storage). The corresponding public key is registered with Wovith's sync server at device authorization time. An auditor can verify the signature and trust that the provenance record is what the device claimed.

This is an opt-in feature for Trust tier. Free and Pro tiers don't get the export.

The export format is W3C PROV-DM-compatible JSON. External tools that consume PROV records (academic data lineage tools, compliance auditors) can read it.

## 10. Performance characteristics

| Operation | Target |
|---|---|
| Recording an entity | < 0.5ms |
| Recording an activity | < 0.5ms |
| Recording a relation | < 0.3ms |
| Querying a cell's lineage (typical) | < 50ms |
| Computing the per-item drill-down | < 200ms |
| Export of one day's provenance | < 5s |

These are achievable because recording is batched and flushed asynchronously, and queries use the indexed `cell_id` columns.

Storage volume: a power user with 50 cells evaluating every few hours generates roughly 5-10 MB of provenance per month. Well within the cache budget.

## 11. Edge cases

### 11.1 Failed evaluations

A cell that fails to evaluate still gets provenance: the activity is recorded with `status: 'failed'`, the failed entity is recorded with the error, and the chain stops at the failure point. The user's "why" answer becomes "this failed because...".

### 11.2 Cancelled evaluations

When a cell evaluation is aborted (the user closed the lens), the activity is recorded with `status: 'cancelled'` and any partial results are tagged accordingly.

### 11.3 Cache hits

A cache hit produces a short provenance chain: cell-evaluation → cache-read → (the cached entity). The user sees "this came from cache, originally fetched X minutes ago."

### 11.4 Background mining

Mining runs in the background and produces a provenance trail just like any other evaluation. When a mined lens proposal is presented to the user, the proposal includes a "what I scanned" summary derived from the provenance.

### 11.5 Multi-device divergence

Two devices show different results for the same cell. The user opens the "why" view on one device; sees that device's provenance. Cross-device comparison ("why does my phone show this but my desktop shows that?") is not supported at v1 — both devices' provenance is self-consistent, just for different evaluation events.
